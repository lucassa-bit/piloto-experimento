## 2. Formato reconhecido

Observado no smoke (`last-message.txt`):

```text
1. [NEEDS CLARIFICATION] <pergunta>?

2. [NEEDS CLARIFICATION] <pergunta>?
...
```

Parser:

- fonte canônica: `attempt-N/last-message.txt`
- item = linha que casa `^\s*\d+[\.)]\s+` ou bullet `[-*]`
- corpo literal **inclui** o marcador `[NEEDS CLARIFICATION]` (sem o token `N.`)
- continuações multiline anexadas ao item corrente
- `NO_CLARIFICATION_NEEDED` (sem markers) → 0 perguntas, `PARSE_OK`
- marker presente sem lista interpretável → `PARSE_REVIEW_REQUIRED` (não inventa split)

`stdout.jsonl` **não** substitui `last-message.txt`; só entra no check de progressão/auto-answer.

## 5. Status finais

### Integridade (`technical_status`)

| Status | Quando |
| --- | --- |
| `TECHNICAL_SUCCESS` | artefatos OK, exit 0, config congelada OK, spec unchanged, identidade/contexto OK, sem progressão/auto-answer |
| `TECHNICAL_FAILURE` | falta artefato, exit ≠ 0, config divergente, identidade/contexto inválidos, etc. |
| `PROTOCOL_VIOLATION` | `spec_sha256_before != spec_sha256_after` (ou flag `protocol_violation`) |

**0 perguntas ≠ falha técnica.**

### Parse (`parse_status`)

| Status | Quando |
| --- | --- |
| `PARSE_OK` | lista numerada/bullet interpretável, ou `NO_CLARIFICATION_NEEDED` |
| `PARSE_REVIEW_REQUIRED` | texto presente sem estrutura confiável |

### Clarification (`clarification_status`)

| Valor | Quando |
| --- | --- |
| `HAS_QUESTIONS` | ≥1 pergunta parseada |
| `NO_CLARIFICATION_NEEDED` | mensagem final indica isso e não há markers de pergunta |
| *(vazio)* | parse em revisão / artefato ausente |

## 7. Limitações conhecidas do parser

- Não interpreta o formato interativo stock `**Question:**` + tabela Option (não visto no smoke audit-only).
- Não usa `stdout.jsonl` como fonte de perguntas.
- Não deduplica semanticamente; não corrige gramática; não mapeia Gap ID.
- Mistura de prosa + markers sem lista → `PARSE_REVIEW_REQUIRED` (conservador).
- Bullets `[-*]` aceitos, mas o smoke real usou só `N.`
